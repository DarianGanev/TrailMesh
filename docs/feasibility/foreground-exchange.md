# Foreground exchange feasibility gate

Issue #2 establishes the smallest transport contract before report storage or routing is added. A platform adapter supplies discovery, consent/authentication, and byte transfer; the shared coordinator bounds the application object at 16 KiB, validates its SHA-256 digest, and records redacted lifecycle evidence.

Run the local contract tests from the repository root:

```text
python -m unittest discover -s tools/transport -p "test_*.py"
```

The local loopback transport is a deterministic development check. It does not prove radio interoperability. Physical Gate A evidence must be recorded in [`evidence-template-v1.json`](../../experiments/foreground_exchange/evidence-template-v1.json) using the selected iPhone and Android devices, with internet disabled while the required local radios remain enabled.

Each physical attempt must record the direction, payload size, adapter and strategy, permission/radio state, consent and authentication results, lifecycle timing, expected and received SHA-256 values, and a structured failure reason. The initial acceptance rule is at least 18 matching 2 KiB exchanges out of 20 in **each direction**. Do not record message contents, private keys, personal routes, or raw contact exports.

## Device probe

The paired native probe is under [`experiments/foreground_exchange`](../../experiments/foreground_exchange/). It is a generated-byte feasibility client, not the complete TrailMesh app. The iOS target uses Swift; the Android target uses Kotlin and Google Nearby Connections 19.5.0. The iOS package is pinned to a source revision in the Xcode project. Both targets use the point-to-point strategy and the same service ID. Version 0.2.0 uses probe-v2 messages and requires both phones to be updated; old probe builds are not compatible. The signed-bundle protocol v1 fixture is unchanged.

Both phones use the same **Start test session** flow and payload-size choice. There is no sender/receiver or platform-mode selector. Android advertises; iPhone discovers Android using BLE. Android pairs elect the initiator from the random session IDs. The connection then exchanges generated bytes in both directions. Discovery pauses during connection/exchange. Completed exchanges release the point-to-point link so another peer can be tested sequentially, with a bounded peer journal. This does not provide simultaneous fan-out or multi-hop relaying. The iPhone-to-iPhone path needs a separate feasibility adapter/gate and is excluded from this pairing contract.

Each peer automatically sends 20 framed payloads and separately counts unique received payloads. HELLO binds both session IDs, the payload size and the fixed attempt count. DATA and ACK name the sender's session and logical attempt; duplicate DATA is acknowledged without increasing the unique count. FINISH and its reciprocal ACK distinguish a finished batch from a disconnected link. Raw parsing is bounded before copies. Literal cross-platform vectors are in [`probe-v2-vectors.json`](../../protocol/probe-v2-vectors.json).

Pending attempts retain their identity across reconnects. Attempts, connection recovery, peer records and diagnostics have limits. A generated payload is acknowledged positively only after acceptance progress has been checkpointed; a storage failure pauses the probe. This is generated-byte evidence, not a durable signed-report receipt. Current adapter/session/endpoint guards discard old callbacks. The exported redacted log includes recovery, duplicate and interruption events, without payloads, SDK authentication tokens, endpoint IDs or Wi-Fi network names.

The probe permits three transmissions per logical attempt, five ordinary connection recoveries, eight peer journals and 512 retained diagnostic records. Backoff is bounded. A reciprocal-completion inactivity deadline releases a link that stays connected while its peer stops progressing. Recently completed peers have a short, bounded control-only reconciliation window; DATA progress is retained and never counted again. Export both logs after each test pair, before later peers or repeated retries evict earlier records from the diagnostic ring.

### Radio policy and observed results

The user reports Android-to-Android batches and iPhone/Android batches reaching 20/20. In the older role-based probe, Android discovery of an iPhone advertiser stalled without network association, while iPhone discovery of Android worked. PR #35's diagnostic mode let both payload directions work over the latter connection. The reports also identify disruption around Wi-Fi auto-association. These observations identify a promising initiation policy, not the exact underlying medium or a completed evidence record.

Android advertising and connection requests now select [NON_DISRUPTIVE](https://developers.google.com/android/reference/com/google/android/gms/nearby/connection/ConnectionType), which instructs Nearby to preserve Wi-Fi/Bluetooth state. It cannot prevent the OS from joining a saved network. The iPhone requests BLE-only discovery and connections using the pinned SDK's public medium option. A network-association event is recorded but does not destroy a healthy link; actual disconnects and protocol deadlines enter recovery. Do not repeatedly toggle Wi-Fi as the application's recovery strategy. Record radio state and network association separately in physical tests.

### Session lifecycle

Android owns the session in a user-started `connectedDevice` foreground service with an ongoing notification and Stop action. Leaving the Activity, opening the share chooser or returning to it no longer cancels the session. Required permissions are checked before service launch. Permission denial and OS/vendor process restrictions can still interrupt operation. A foreground service is not a promise of survival after Task Manager Stop, force stop or process termination. [Android service requirements](https://developer.android.com/develop/background-work/services/fgs/service-types#connected-device)

The iOS model is app-owned and checkpoints intention and progress. On iOS 26+, a real local Live Activity started while foregrounded after BLE setup, together with `bluetooth-central`, enables a supported background-scan integration to test. Activity authorization failure, dismissal or ending falls back to bounded finishing and saved pause/resume. Live Activities have an eight-hour active limit. Older iOS versions use the finite background-task fallback. Returning to the app resumes saved progress automatically after ordinary backgrounding; a cold launch offers Resume rather than pretending an old SDK connection survived. [Core Bluetooth](https://developer.apple.com/documentation/corebluetooth), [ActivityKit](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities), [finite background execution](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time)

Apple explicitly qualifies the Live Activity scan privilege when a locked display turns fully off: scanning restrictions change again, with no supported workaround for that broader privilege. The pinned Nearby SDK also exposes no restoration identifiers. Keep fresh discovery while screen-off, actual background transfer and process termination as distinct gates; a displayed Live Activity or saved session is not evidence of a working radio link. [Apple engineer response](https://developer.apple.com/forums/thread/815189), [Bluetooth restoration rules](https://developer.apple.com/documentation/technotes/tn3115-bluetooth-state-restoration-app-relaunch-rules)

If Android advertising or discovery fails to start, the status and redacted test log show the Google Play Services status code and name when available, plus the exception type. Share the test log so the failure can be diagnosed; it omits raw exception messages and test payload bytes.

Compatibility observation: on Android 13, this probe first received Google Nearby status `8034` (`MISSING_PERMISSION_ACCESS_COARSE_LOCATION`) at discovery start even though Nearby devices permission was enabled. After approximate Location was granted, the same device returned `8036` (`MISSING_PERMISSION_ACCESS_FINE_LOCATION`). Android 13+ startup requests Nearby permissions, with a Location prompt through the visible Activity when a matching SDK permission failure requires it. Older versions include their Location prerequisites. Permission responses are bound to the current request and readiness is rechecked. These are observed SDK/device behaviors, not claims that all Android 13 devices require Location. The probe does not read or log coordinates. See Google's [status code reference](https://developers.google.com/android/reference/com/google/android/gms/nearby/connection/ConnectionsStatusCodes).

Connection requests and Nearby's verification callback are automatically accepted only after the user starts this test session. This deliberately avoids a per-encounter tap in the probe. Google warns that automatically accepting the short verification token does not authenticate the peer, so the probe must carry generated test bytes only. This is not the production security policy.

### Build and install

For Android, open `experiments/foreground_exchange/android` in Android Studio, use JDK 17 for Gradle, sync the project, and install the `app` debug configuration. The command-line build and unit tests are:

```powershell
cd experiments/foreground_exchange/android
.\gradlew.bat testDebugUnitTest assembleDebug
```

For iOS, open `experiments/foreground_exchange/ios/TrailMeshTransportProbe.xcodeproj` in Xcode, select the `TrailMeshTransportProbe` scheme and the iPhone, then build and run it. Allow Bluetooth and Local Network access when iOS asks. The iOS frame tests run in CI on an iPhone simulator.

#### Windows and AltStore Classic test path

The Quality workflow builds an **unsigned iPhone-device IPA** including the session Live Activity extension and uploads it as the `TrailMeshTransportProbe-unsigned-iphoneos` artifact. Its `SHA256SUMS.txt` identifies the package to test. A simulator `.app` cannot be substituted for it. Android's debug APK is uploaded as `TrailMeshTransportProbe-android-debug`; local output remains `app/build/outputs/apk/debug/app-debug.apk`.

1. Install [iTunes and iCloud directly from Apple](https://faq.altstore.io/altstore-classic/how-to-install-altstore-windows), then install [AltServer for Windows](https://altstore.io/). Use **AltStore Classic** for IPA files; AltStore PAL does not import arbitrary IPA files.
2. Connect and unlock the iPhone, trust the computer when prompted, and use AltServer to install AltStore Classic. Complete Apple ID sign-in on your own device and PC. Enable Wi-Fi sync if using wireless refresh. Complete the iPhone's trust and Developer Mode steps in the [AltStore Windows guide](https://faq.altstore.io/altstore-classic/how-to-install-altstore-windows).
3. Download and extract the artifact from the successful GitHub Actions run. Verify the IPA's SHA-256 against `SHA256SUMS.txt`. Import the IPA into AltStore Classic on the iPhone, or use AltServer's **Shift-click → Sideload .ipa** option on Windows. AltStore/AltServer signs it for the test phone; never commit Apple credentials or signing material to this repository.
4. Open the probe and allow the Bluetooth and Local Network prompts. If the install or first launch fails, record the exact error and iOS version. Installation and each payload direction must be documented in Issue #2's physical evidence record.

Refresh the sideloaded app before its displayed expiry. Keep AltServer reachable from the iPhone; a USB connection also works. AltStore attempts background refresh, but it is not guaranteed. [AltStore refresh instructions](https://faq.altstore.io/altstore-classic/your-altstore), [AltServer connection instructions](https://faq.altstore.io/altstore-classic/altserver).

### Run the physical gate

1. Update every test phone to the same probe version. Keep both apps open and unlocked for the initial gate.
2. Disable mobile data, disconnect from internet-connected Wi-Fi, disable hotspots, and keep Bluetooth on. Record Wi-Fi radio enabled/disabled and network association independently. Repeat with Wi-Fi disabled in Settings to characterize the BLE-oriented path.
3. Choose the same size on both phones, then start a session on each. The apps automatically connect and exchange 20 attempts in each direction. Repeat at 256 bytes, 2 KiB and 8 KiB, stopping both sessions before changing size. Save both logs after each run.
4. Record exact models, OS/MIUI/Google Play Services versions, app version/build, SDK revision, permissions, radios, network association, consent/authentication behavior and every attempt in `evidence-template-v1.json`. Internet-disabled is a manually recorded condition; the apps cannot infer it from a radio toggle. Do not include payload bytes or authentication tokens.
5. Issue #2 passes only if the 2-KiB batch has at least 18 matching results out of 20 in each direction and receiver records corroborate unique deliveries. Retries and duplicates are not extra successes. Foreground results do not establish background behavior.

Check the two v2 device exports from the repository root:

```text
python -m tools.transport.validate_probe_logs path/to/first-log.json path/to/second-log.json
```

The validator checks both complete 20-attempt batches, unique logical indices, current peer/session correlation, generated-byte digests and corresponding receiver evidence. Use `--payload-size 256` or `--payload-size 8192` for the optional sizes. Logs cannot establish radio settings, lack of internet or screen/background conditions; record those observations separately. Keep raw device exports in an ignored `device-logs/` folder.

### Interruption and lifecycle matrix

Run each condition separately on both Android models and the exact target iPhone/iOS build. Preserve failures and inconclusive results.

| Condition | Required observation |
|---|---|
| Both launch orders; different sizes; old version | Deterministic compatible pairing or explicit refusal, no false success. |
| Android Home/app switch/share chooser/rotation | Same session ID and progress; service notification stays available; no Activity-owned cancellation. |
| Android notification denied; Stop; Task Manager Stop; force stop | Correct stopped/interrupted state and no unrequested restart. |
| Saved Wi-Fi auto-association/roaming; Wi-Fi toggle; Bluetooth toggle | Healthy links not destroyed by mere default-network changes; disconnect recovery bounded; same attempt identity retained. |
| Range loss before ACK, then return | Duplicate-safe re-ACK and one unique result; no skipped attempt or inflated count. |
| Permission revoked; compatibility prompt denied or answered after Stop | Clear paused state, stale callback ignored, no background permission dialog or automatic restart. |
| iPhone background behind another app, then foreground | Intent and counters preserved; actual data completion distinguished from saved progress. |
| iOS26 Live Activity enabled, denied, dismissed, ended | Supported BLE integration or saved fallback; ending activity never erases progress. |
| iPhone locked/display on versus fully off for 1/5/15/30 minutes | Fresh discovery and transfers measured separately from existing connection retention. |
| Advertiser starts after iPhone backgrounds; both phones background | New discovery proven by correlated transfer logs, not an active-session label. |
| Cold launch; checkpoint corruption/storage failure | Explicit Resume/interrupted/error state; no invented durable acceptance. |
| Three phones, sequential encounters; extra incoming endpoint | Fair bounded serial exchange or rejected busy peer; never simultaneous fan-out or claimed multi-hop relay. |

The final product requires signed report validation, transactional report storage, verified-contact encryption, relevance filtering and store-carry-forward routing. Probe session IDs/checksums and automatic Nearby verification do not implement those protections. Issue #36 delivers this hardened probe; #27 and the durable-exchange issues retain the production gates.

If the phones cannot discover or connect, preserve the failed logs and reasons. Do not substitute loopback, simulator, or LAN results for this physical test.
