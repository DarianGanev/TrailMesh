# TrailMesh

TrailMesh is an iPhone-first, Android-compatible outdoor application for sharing fresh trail information without depending on internet access at the moment of exchange.

Phones store signed reports and encrypted messages, carry them while people move, and exchange selected data during later encounters. The project studies opportunistic networking, store-carry-forward routing, freshness, evidence, privacy, and the practical limits imposed by mobile operating systems.

## Current phase

M1 transport feasibility is complete. The repository contains native iPhone and Android transport probes, a frozen signed-bundle protocol fixture, and shared Python validation tools. M2 adds durable signed reports, expiry and deduplication, three-device relaying, and the first map/report interface.

The native products include GRDB (iPhone) and Room (Android) report repositories with protected signing identities and tests against the [signed public-report admission profile](protocol/report-v1-profile.json), the Python reference validator, and [shared valid/invalid vectors](protocol/report-v1-vectors.json). Android encrypts its Ed25519 seed with a non-exportable Android Keystore AES key; the Ed25519 seed itself is not a non-exportable Keystore key. Transport-independent encounter engines use the [bounded report-exchange contract](protocol/exchange-v1-profile.json) and [literal frame vectors](protocol/exchange-v1-vectors.json). Session interface and physical acceptance remain tracked in #27. The probes still exchange generated test bytes.

Inspect a shared case without changing its literal bytes with `python -m tools.protocol.inspect_report_vector frozen-v1`. Shared-vector tests do not establish physical iPhone-to-Android report exchange.

Open **Nearby** in Explore to share signed public reports for a selected route or map area. Android runs a user-started foreground service and offers a Stop action in the notification when notifications are allowed. Keep TrailMesh in the foreground on iPhone. **Developer tools** provides a separate session for synthetic reports and redacted relay evidence. Physical acceptance for exchange, restart and relaying is tracked in [#4](https://github.com/DarianGanev/TrailMesh/issues/4) and [#54](https://github.com/DarianGanev/TrailMesh/issues/54). See the [product session test procedure](TrailMesh.md#product-session-development-test).

Local report selection follows the [relevance profile](protocol/relevance-v1-profile.json) and [shared decision cases](protocol/relevance-v1-vectors.json). A configured area or local route corridor selects fresh reports without transmitting route geometry or interest hints. Missing usable configuration produces an explicit configuration-required result. Exchange inventories preserve their existing ID order while filtering bounded candidate pages. Native repositories also expose observation-ordered pages that inspect at most 64 reports per call for future map/history consumers.

If a corrected device clock moves backwards, the repository reports a clock error. After explicit user confirmation, clock recovery quarantines existing reports as history; it does not forward or display them as current. Quarantined reports count against storage limits until their signed expiry. To avoid deleting data under an incorrect clock, expired reports remain visible as history until the user confirms the clock and chooses storage cleanup. The development panel exposes explicit clock-recovery and cleanup confirmations.

Both probe apps use **Start test session** to send and receive generated bytes automatically. Physical tests on an iPhone 17 and a Redmi Note 11 Pro 5G running Android 13 recorded 20/20 exchanges in each direction at 256 bytes, 2 KiB, and 8 KiB, with Wi-Fi and mobile data disabled and Bluetooth enabled. A separate 2 KiB test also completed 20/20 in each direction after backgrounding; the device owner reported both displays were off.

The [physical evidence](probes/transport/evidence-physical-v1.json) records the setup and results. These tests establish the generated-byte transport baseline. Product signed-report relay evidence is tracked in #4. Private messaging and offline maps have their own later delivery gates.

The current probe builds use Nearby's cluster strategy with up to four connecting or active neighboring links per phone. Both platforms advertise and discover, including iPhone-to-iPhone encounters. Each link has independent protocol state, deadlines and recovery. Waiting candidates take released slots. A controlled test run retains at most eight peer journals; starting a new run resets this evidence bound. These are initial resource limits. The existing physical evidence covers the earlier point-to-point builds, and simultaneous cluster radios still require physical testing. All test phones must install matching cluster builds. See the [multi-phone test procedure](TrailMesh.md#multi-phone-cluster-probe-procedure).

The product flow is: prepare a map, start a trail session once, and let eligible reports exchange during encounters. Explore remains the home screen. Broader device and lifecycle coverage will be measured as the product grows.

## Repository layout

`probes/transport/` is the synthetic-byte feasibility probe, not a product app. `protocol/` holds shared contracts and vectors; `tools/` holds reference implementations and validation utilities. Native product targets live under `apps/`.

```text
apps/ios/                     iPhone product target and signed-report repository
apps/android/                 Android product target and Room report repository
protocol/                     Signed-report admission profile, fixtures, and wire vectors
tools/protocol/               Admission, canonicalization, and signature reference tests
tools/transport/              Exchange contracts and redacted-log validation
probes/transport/
  android/                    Kotlin Android probe and unit tests
  ios/                        SwiftUI iPhone probe, Live Activity, and tests
  evidence-physical-v1.json    Recorded M1 device evidence
  evidence-template-v1.json    Template for additional physical tests
.github/                      CI workflow and dependency updates
TrailMesh.md                  Product, engineering, and diploma specification
```

## Development principles

- Work through short-lived feature branches and pull requests.
- Keep `main` releasable and use `develop` as the integration branch.
- Record platform behavior as measured evidence, not assumptions.
- Keep public reports immutable and private messages end-to-end encrypted.
- Label simulations, physical tests, and unverified claims clearly.
- Do not commit credentials, private keys, personal routes, or raw contact exports.

## Local checks and device builds

Run the reference tests from the repository root with Python 3.11 or newer:

```powershell
python -m pip install -r tools/protocol/requirements.txt
python -m unittest discover -s tools/protocol -p "test_*.py"
python -m unittest discover -s tools/transport -p "test_*.py"
```

On a Mac with Xcode 16.4 and Swift 6.1, run the iPhone product repository tests with `cd apps/ios && swift test`. The product app project is `apps/ios/Product/TrailMesh.xcodeproj`; its bundle identifier and unsigned CI artifact are distinct from the transport probe. CI also tests the repository on an iPhone simulator. The product target is a development build with public-report session diagnostics. Its physical radio and lifecycle results require the recorded product-session procedure.

The offline hiking backend uses MapLibre Native and a local Valhalla graph. Product iPhone builds require iOS 17.0 or later; the independent report package retains its existing platform floor. [Region tooling](tools/maps/README.md) prepares a licensed Rila map, elevation shading, named-place search index, and routing graph from frozen source data. It includes mapped minor paths, huts and peaks. OpenStreetMap completeness and current trail safety remain separate concerns.

The iPhone product uses an [isolated native routing framework](apps/ios/NativeRouting/README.md) to keep its C++ dependencies separate from Nearby. Xcode verifies the pinned release archive automatically. CI also builds the framework from its documented inputs.

Explore opens to the interactive Rila map once its verified download is saved. The first launch offers **Download Rila** (about 64 MB), and subsequent launches open the saved map offline. Report workflows and route selection remain tracked in [#26](https://github.com/DarianGanev/TrailMesh/issues/26).

Install `tools/maps/requirements.txt`, then run `python -m unittest discover -s tools/maps -p "test_*.py"` for map-pack contract checks. The native development diagnostics accept a separately pinned manifest hash and HTTPS release directory, then install verified resources into app-private storage. Native offline tests consume the real prepared region, block renderer HTTP requests, calculate a hut-to-peak route, retain screenshots, and reopen saved resources after process shutdown. Recorded CI and physical-device evidence establish which of those checks have passed. The calculated native route is also passed through the existing relevance policy: a report on its geometry must be eligible and a Sofia report must be excluded. Transport diagnostics retain their fixed Sofia area for repeatable radio tests. Product route selection under #26 will call the existing session coordinator context-update API; installing or calculating a diagnostic route does not change an active transport session.

Build and test the Android product with JDK 17 and the Android SDK configured:

```powershell
cd apps/android
.\gradlew.bat testDebugUnitTest assembleDebug assembleDebugAndroidTest
# With an API 26+ emulator connected:
.\gradlew.bat connectedDebugAndroidTest
```

See [Android product storage](apps/android/README.md) for repository APIs, migrations, key protection, test scope, and limitations. The product application ID is `org.trailmesh.app`; it coexists with the transport probe.

Build the independent Android transport probe:

```powershell
cd probes/transport/android
.\gradlew.bat testDebugUnitTest assembleDebug
```

The APK is generated at `app/build/outputs/apk/debug/app-debug.apk`. Successful platform CI runs publish the Android APK and an unsigned iPhone IPA. The [specification](TrailMesh.md#64-build-install-and-test-cycle) describes installing the IPA using AltStore/AltServer and exporting test logs.
