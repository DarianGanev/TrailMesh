# TrailMesh

TrailMesh is an iPhone-first, Android-compatible outdoor application for sharing fresh trail information without depending on internet access at the moment of exchange.

Phones store signed reports and encrypted messages, carry them while people move, and exchange selected data during later encounters. The project studies opportunistic networking, store-carry-forward routing, freshness, evidence, privacy, and the practical limits imposed by mobile operating systems.

## Project specification

Read [TrailMesh.md](TrailMesh.md) for the complete product, protocol, security, testing, evaluation, and nine-month delivery plan.

The map-first screen hierarchy, accessibility direction, and trail-session interaction are described in [TrailMesh.md](TrailMesh.md). Project milestones and work tracking are maintained in GitHub.

## Current phase

M1 transport feasibility is complete. The repository contains native iPhone and Android transport probes, a frozen signed-bundle protocol fixture, and shared Python validation tools. M2 adds durable signed reports, expiry and deduplication, three-device relaying, and the first map/report interface.

The native products include GRDB (iPhone) and Room (Android) report repositories with protected signing identities and tests against the [signed public-report admission profile](protocol/report-v1-profile.json), the Python reference validator, and [shared valid/invalid vectors](protocol/report-v1-vectors.json). Android encrypts its Ed25519 seed with a non-exportable Android Keystore AES key; the Ed25519 seed itself is not a non-exportable Keystore key. Report transport integration remains separate work. The probes still exchange generated test bytes.

Inspect a shared case without changing its literal bytes with `python -m tools.protocol.inspect_report_vector frozen-v1`. Shared-vector tests do not establish physical iPhone-to-Android report exchange.

If a corrected device clock moves backwards, the repository reports a clock error. After explicit user confirmation, clock recovery quarantines existing reports as history; it does not forward or display them as current. Quarantined reports count against storage limits until their signed expiry. To avoid deleting data under an incorrect clock, expired reports remain visible as history until the user confirms the clock and chooses storage cleanup. The development app does not yet expose these recovery and cleanup flows.

Both probe apps use **Start test session** to send and receive generated bytes automatically. Physical tests on an iPhone 17 and a Redmi Note 11 Pro 5G running Android 13 recorded 20/20 exchanges in each direction at 256 bytes, 2 KiB, and 8 KiB, with Wi-Fi and mobile data disabled and Bluetooth enabled. A separate 2 KiB test also completed 20/20 in each direction after backgrounding; the device owner reported both displays were off.

The [physical evidence](probes/transport/evidence-physical-v1.json) records the setup and results. These tests establish the generated-byte transport baseline; signed-report exchange, private messaging, offline maps, and multi-hop delivery are upcoming work.

The product flow is: prepare a map, start a trail session once, and let eligible reports exchange during encounters. Explore remains the home screen. Broader device and lifecycle coverage will be measured as the product grows.

## Repository layout

`probes/transport/` is the synthetic-byte feasibility probe, not a product app. `protocol/` holds shared contracts and vectors; `tools/` holds reference implementations and validation utilities. Native product targets live under `apps/`.

```text
apps/ios/                     iPhone product target and signed-report repository
apps/android/                 Android product target and Room report repository
protocol/                     Signed-report admission profile, fixtures, and wire vectors
tools/protocol/               Admission, canonicalization, and signature reference tests
tools/transport/              Exchange contracts and redacted-log validation
probes/transport/
  android/                    Kotlin Android probe and unit tests
  ios/                        SwiftUI iPhone probe, Live Activity, and tests
  evidence-physical-v1.json    Recorded M1 device evidence
  evidence-template-v1.json    Template for additional physical tests
.github/                      CI workflow and dependency updates
TrailMesh.md                  Product, engineering, and diploma specification
```

## Development principles

- Work through short-lived feature branches and pull requests.
- Keep `main` releasable and use `develop` as the integration branch.
- Record platform behavior as measured evidence, not assumptions.
- Keep public reports immutable and private messages end-to-end encrypted.
- Label simulations, physical tests, and unverified claims clearly.
- Do not commit credentials, private keys, personal routes, or raw contact exports.

## Local checks and device builds

Run the reference tests from the repository root with Python 3.11 or newer:

```powershell
python -m pip install -r tools/protocol/requirements.txt
python -m unittest discover -s tools/protocol -p "test_*.py"
python -m unittest discover -s tools/transport -p "test_*.py"
```

On a Mac with Xcode 16.4 and Swift 6.1, run the iPhone product repository tests with `cd apps/ios && swift test`. The product app project is `apps/ios/Product/TrailMesh.xcodeproj`; its bundle identifier and unsigned CI artifact are distinct from the transport probe. CI also tests the repository on an iPhone simulator. The product target is a development build and does not yet exchange reports over radio.

Build and test the Android product with JDK 17 and the Android SDK configured:

```powershell
cd apps/android
.\gradlew.bat testDebugUnitTest assembleDebug assembleDebugAndroidTest
# With an API 26+ emulator connected:
.\gradlew.bat connectedDebugAndroidTest
```

See [Android product storage](apps/android/README.md) for repository APIs, migrations, key protection, test scope, and limitations. The product application ID is `org.trailmesh.app`; it coexists with the transport probe.

Build the independent Android transport probe:

```powershell
cd probes/transport/android
.\gradlew.bat testDebugUnitTest assembleDebug
```

The APK is generated at `app/build/outputs/apk/debug/app-debug.apk`. Successful platform CI runs publish the Android APK and an unsigned iPhone IPA. The [specification](TrailMesh.md#64-build-install-and-test-cycle) describes installing the IPA using AltStore/AltServer and exporting test logs.
